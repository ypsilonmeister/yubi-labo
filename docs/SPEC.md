# 直感算数クラフト（仮）Webアプリケーション 要件定義・基本設計書

## 1. プロジェクト概要と背景（開発者向けドメイン知識）

### 1.1 開発の目的
本プロジェクトは、**「掛け算・割り算や人生ゲームの計算（全体構造やシステムの理解）は得意だが、1桁の足し算（$2 + 3$ など）や $6 \cdot 7 \cdot 8$ の識別、位取り・繰り上がり・繰り下がりでつまずく」**という認知特性を持つ子どものために、脳のオーバーヒート（生あくび・疲労）を起こさず、直感的・視覚的に数の合成・分解・位取りを習得できるブラウザ完結型ゲームを開発することである。

### 1.2 対象ユーザーの認知特性（なぜつまずくのか？）
* **得意な処理（トップダウン・構造処理）：**
  * 掛け算（$3 \times 4$ など）のような「同じ塊の繰り返し（対称的な構造・リズム）」や、人生ゲームのお札（$\$1,000$, $\$5,000$, $\$10,000$）のような「明確にルール化された単位の交換システム」はスムーズに処理できる。
* **苦手な処理（ボトムアップ・数え足し・非対称の合成）：**
  * **カウンティングの負荷：** $2 + 3$ を見たとき、構造のヒントがないため「$1, 2, 3\dots$」と1つずつ数え上げる処理になり、ワーキングメモリを激しく消費する。
  * **非対称パーツの合成エラー：** 指やタイルで「$5$ と $2$」を見せられた際、脳内で瞬時に「$7$」という1つの概念にチャンク化（合成）できず、「$5$ と $2$ という別々のパーツが並んでいる」状態から1つずつ数え直してしまう。
  * **視覚ノイズによるオーバーヒート（あくびの正体）：** 従来の水道方式動画のような「同色（水色一色）で縦1列に積まれたタイル」では、$6 \cdot 7 \cdot 8$ の境目が視覚的に溶けてしまい、長さを目測で測ろうとして脳が酸欠（生あくび連発）を起こす。
  * **さくらんぼ計算の手順パンク：** 「$8 + 5$」を「$5$ を $2$ と $3$ に分けて、$8$ と $2$ で $10$ を作り…」と頭の中で4ステップ保持する処理が大きなストレスになる。

## 2. UI/UX 絶対遵守ルール（コア・ガイドライン）

どのゲームモードを実装・追加する場合も、以下の4つのルールを共通仕様として厳守する。

1. **【禁止】数式テキストの直接提示**
   * 問題として画面に `$2 + 3 = ?$` や `$13 - 8 = ?$` といった算数の式を出さない（見た瞬間に「苦手な勉強」として脳がシャットダウンするため）。
   * ※パズルがハマった**結果のエフェクト**として、画面に大きく数字や構造が表示されるのはOK。
2. **【禁止】制限時間（タイマー・カウントダウン）の表示**
   * 画面上に残り時間ゲージやカウントダウンを出さない（焦りがワーキングメモリを圧迫するため）。
   * ※ただし、**裏側（バックグラウンド）ではミリ秒単位で回答時間を計測**し、迷い度合い（脳の負荷）の分析データとして保存する。
3. **【禁止】同色・縦1列のタイル配置、および無意味に動くオブジェクト**
   * $5$ を超える数を同色・1列で並べない。また、画面内でオブジェクトを散乱させたり移動させたりしない（眼球運動にメモリを奪われないよう、常に画面中央の固定フレーム内で完結させる）。
4. **【必須】「空席（補数）の可視化」と「自動合体・分裂アニメーション」**
   * 頭の中で数を割ったり移動させたりする負荷を減らすため、ブロックを枠に近づける・ぶつけるだけで「パカッと割れて空席に吸い込まれ、満タンになって進化する」という**物理現象としてのアニメーション**を自動再生し、視覚イメージを脳に刷り込む。

## 3. システムアーキテクチャ設計

### 3.1 技術スタック要件
* **動作環境：** モダンWebブラウザ（PC / タブレット / スマートフォン対応、タッチ操作およびドラッグ＆ドロップ最適化）

* **データ永続化：** ブラウザの `localStorage` を使用（バックアップ用のJSONエクスポート/インポート機能を実装）

### 3.2 モード切替と拡張性を担保する「プラグイン型設計」
すべての案（モード）を自由に切り替えられ、将来新しいアイデアが出た際に1ファイル（または1クラス）追加するだけでシステムに組み込めるよう、**共通のゲームエンジン・インターフェース（Strategyパターン）**を採用する。

```
[ App Shell (共通ヘッダー / モード切替ランチャー / 音声・エフェクト管理) ]
       │
       ├── [ Problem Generator (出題エンジン: 課題カテゴリ別に数値ペアを生成) ]
       ├── [ Storage & Analytics Manager (localStorage保存・保護者用ダッシュボード) ]
       │
       └── [ Game Mode Registry (プラグイン管理) ]
               ├── Mode A: ヌミコン型（偶奇・対称パズル）
               ├── Mode B: キュイゼネール型（カラーロッド・クラフト）
               ├── Mode C: スライムRPG型（10フレーム・オーバーフロー）
               ├── Mode D: ギルド両替商型（人生ゲーム拡張・通貨システム）
               └── Mode X: ★今後追加する新規モード（共通IFを実装するだけで追加可能）
```

#### 新規モード追加のための共通インターフェース仕様 (`GameModePlugin`)
新しいゲーム案を追加する際は、以下の構造を持つオブジェクトを `GameRegistry.register(plugin)` に渡すだけで、メニュー画面と成績記録に自動反映される設計とする。

```javascript
/**
 * 各ゲームモードが実装すべき共通インターフェース
 */
const GameModePluginTemplate = {
  id: "mode_unique_id",          // モード識別子 (例: 'numicon_puzzle')
  title: "モード表示名",          // メニューに表示する名前
  description: "モードの説明",    // 保護者向けの狙い解説
  supportedTasks: [              // このモードが対応する学習課題カテゴリ
    "subitizing_678",            // 6・7・8の瞬時認識
    "synthesis_5",               // 5までの合成 (2+3など)
    "complement_10",             // 10の補数
    "carry_over",                // 繰り上がり加算 (8+5など)
    "borrow"                     // 繰り下がり減算 / お釣り逆算 (13-5など)
  ],

  // モード開始時の初期化処理（DOMコンテナを受け取る）
  init(containerElement, context) {},

  // 問題データを受け取り、画面を描画する
  // question例: { taskType: 'carry_over', base: 8, target: 5, answer: 13 }
  loadQuestion(questionData) {},

  // 終了・別モードへの切り替え時のクリーンアップ処理
  destroy() {}
};
```

## 4. 実装する各ゲームモード（4案）の詳細仕様

### 【案A】『偶奇・対称パズル（ヌミコン × テトリス方式）』
**狙い：** $6 \cdot 7 \cdot 8$ の迷いを「偶奇の対称性（形）」で瞬殺し、$2 + 3$ を「出っ張りの噛み合わせ」として処理する。

* **UIデザイン（2列プレート構造）：**
  * 1〜10の数を、ドット（穴）が**「2列」**に並んだプレートとして表現する。
  * **偶数（$2, 4, 6, 8, 10$）：** 左右対称のきれいな長方形（例：$6 = 2 \times 3$、$8 = 2 \times 4$）。
  * **奇数（$1, 3, 5, 7, 9$）：** 長方形の端に**1マスだけポコッと出っ張り（凸）がある非対称な形**。
  * 数値ごとに固有のカラーを固定する。
* **ゲームメカニクス：**
  * **$6 \cdot 7 \cdot 8$ の識別ステージ：** 6（3列の長方形）、8（4列の長方形・10の枠から2マス空席）、7（出っ張りがある形）のシルエットが提示され、手元のプレートを瞬時にハメる。
  * **合成ステージ（$2 + 3 = 5$、$3 + 3 = 6$ など）：**
    * 「$5$ の空き枠（1個出っ張りがある溝）」に対し、手元の「$2$（平坦な長方形）」と「$3$（出っ張りがあるプレート）」をドラッグしてハメると、ガチャンと合体して「$5$ のプレート」に変化する。
    * 奇数＋奇数（例：$3 + 3$）の場合、互いの「1マスの出っ張り」がパズルのように噛み合い、きれいな長方形（$6$）になるアニメーションを見せる。

### 【案B】『カラーロッド・クラフト（キュイゼネール・ロッド方式）』
**狙い：** 目盛り（数える手がかり）を完全に撤廃し、得意な「掛け算・割り算」と同じ「長さと色の比率」で足し算・引き算を処理する。

* **UIデザイン（目盛りなしの色棒）：**
  * 1〜10の数を「一切の区切り線（目盛り）がないカラフルな棒」として描画する。
  * 配色標準：$1=$白、$2=$赤、$3=$黄緑、$4=$ピンク、$5=$黄、$6=$濃緑、$7=$黒、$8=$茶、$9=$青、$10=$オレンジ。
* **ゲームメカニクス：**
  * **等価交換クラフト（$2 + 3 = 5$）：**
    * 画面中央に基準となる「黄色い棒（$5$）」または「長さ $5$ の橋の隙間」がある。
    * 下部にすでに配置されている「赤い棒（$2$）」の横に、手札から「黄緑の棒（$3$）」を選んで繋げると、長さがピタリと一致して橋が完成し、2本の棒が光って「黄色い棒（$5$）」に融合する。
  * **掛け算からの逆輸入アシスト：**
    * もし「$2 + 3$」で迷った場合、ヒントボタンを押すと「赤（$2$）が2本（$2 \times 2 = 4$）＋白（$1$）」のガイド線がうっすら表示され、得意な掛け算（ペア）を基準に長さを特定できるギミックを入れる。

### 【案C】『スライム・オーバーフロー（10フレーム繰り上がり・位取りRPG）』
**狙い：** さくらんぼ計算を頭でやらせず、繰り上がり・繰り下がりを「容量10の器の満杯（オーバーフロー）と上位モンスターへの進化」として自動化・視覚化する。

* **UIデザイン（卵パック型10フレーム）：**
  * 画面右側に「1の位の部屋（$2 \times 5$ マスの10フレーム容器）」、左側に「10の位の部屋（キングスライム待機枠）」を配置。
  * **重要ギミック：** 10フレーム内にスライムが入っているとき、**「空いているマス（空席＝10の補数）」が明るく点滅・ハイライト**される（例：$8$ 入っているときは、空席の $2$ マスが目立つように光る）。
* **ゲームメカニクス：**
  * **繰り上がり加算（例：$8 + 5$）：**
    1. 1の位の容器に $8$ 匹のスライムが入っており、**空席が $2$ マス光っている**。
    2. プレイヤーが手元の「$5$ の塊スライム」を容器に向かってスワイプ（投げ込む）する。
    3. **【自動アニメーション】** 投げ込まれた「$5$」が容器のフチで自動的に「$2$」と「$3$」にパカッと分裂！
    4. 「$2$」が空席に吸い込まれて容器が $10$ 満タンになり、ファンファーレと共に合体して**「キングスライム（$10$）」に進化**し、左の「10の位の部屋」へジャンプする。
    5. 1の位の容器には、あふれた「$3$」がコロンと残る（画面上部に『$1$（キング）と $3$ ＝ $13$ ダメージ！』と表示）。
  * **繰り下がり減算（例：$13 - 5$）：**
    1. 1の位の「$3$」だけでは攻撃（またはバリア解除）に足りないため、左の部屋にいる「キングスライム（$10$）」をタップして爆破（両替）する。
    2. キングスライムから直接「$5$」が撃ち出されて相殺され、残った「$5$」と元の「$3$」がガチャンと合体して「$8$」になる（減加法の一連の流れをワンタップの爽快なエフェクトで見せる）。

### 【案D】『ギルドの高速両替商（人生ゲーム拡張・通貨システム型）』
**狙い：** タイルの面積や長さを一切使わず、すでに得意な「人生ゲームのお札計算」のルールを10進法の位取りと1桁計算にそのまま適用する。

* **UIデザイン（トレイと3種の通貨）：**
  * 通貨アイテム：「銅貨（$1$）」「五つ星トークン（$5$ ※ON/OFF設定可能）」「銀貨（$10$）」「金貨（$100$）」。
  * 面積はすべて同じコイン/お札サイズとし、色と数字・エンブレムで価値を区別する。
* **ゲームメカニクス：**
  * **鉄の掟（所持上限ルール）：** 「手元のトレイには、同じコインを $9$ 枚までしか置けない。$10$ 枚になった瞬間、両替スロットが光って上位コイン $1$ 枚に強制変換される」。
  * **お釣り方式による引き算（例：$13 - 8$）：**
    * 「引き算」という概念を使わず、すべて**「お店屋さんの会計とお釣り（足し算の逆算）」**として演出する。
    * 「銅貨 $8$ 枚のアイテムを買う客が、銀貨 $1$ 枚（$10$）と銅貨 $3$ 枚を出した。$8$ にあと何枚足せば銀貨 $1$ 枚（$10$）になる？」→「銅貨 $2$ 枚！それと残りの $3$ 枚を合わせて、お釣りは $5$ 枚（または五つ星トークン $1$ 枚）！」と処理させる。

## 5. データ保存（`localStorage`）と保護者用ダッシュボード仕様

子どもの「どのUIならあくびが出ないか（反応が速いか）」「どの数字の合成で詰まっているか」を客観的に把握するため、すべてのプレイログを `localStorage` に記録し、後からグラフや表で見返せる保護者画面（管理画面）を実装する。

### 5.1 `localStorage` データスキーマ設計
キー名：`math_craft_app_data_v1`

```json
{
  "profile": {
    "playerName": "プレイヤー",
    "preferredMode": "mode_a_numicon",
    "settings": {
      "soundEnabled": true,
      "highlightEmptySlots": true,
      "autoSplitAnimationSpeed": "normal"
    }
  },
  "logs": [
    {
      "id": "uuid-1234-5678",
      "timestamp": "2026-10-17T07:00:00.000Z",
      "modeId": "mode_c_slime_rpg",
      "taskCategory": "carry_over",
      "problemKey": "8+5",
      "numbers": [8, 5],
      "targetAnswer": 13,
      "isCorrect": true,
      "mistakeCount": 0,
      "usedHint": false,
      "responseTimeMs": 3240,
      "fatigueWarning": false
    }
  ]
}
```

#### 重要メトリクス：`responseTimeMs`（回答所要時間）と `fatigueWarning`（脳疲労サイン）
* 画面にタイマーは表示しないが、問題が表示されてからクリアするまでの時間をミリ秒単位で `responseTimeMs` に記録する。
* 直近の平均回答時間よりも極端に時間がかかった場合（例：$8,000\text{ ms}$ 以上）、裏側で「1つずつ数え直している」または「あくび（脳の疲労）が出ている」可能性が高いため、`fatigueWarning: true` のフラグを立てる。

### 5.2 保護者用ダッシュボード（振り返り画面）の要件
ゲーム画面の隅にあるロック付きボタン（長押しまたは大人向けパスコード）から開ける分析ビュー。

1. **モード別「脳へのフィット度」比較レポート**
   * 案A（ヌミコン型）、案B（カラーロッド型）、案C（スライムRPG型）、案D（ギルド両替商型）のそれぞれについて、**「平均回答スピード」「ミス率」「脳疲労サイン（長考）の発生率」**を一覧比較する。
   * これにより、「うちの子には案Aと案Cのハイブリッドが一番合っている」といった判断がデータで可能になる。
2. **苦手パターン・ヒートマップ**
   * **「$6 \cdot 7 \cdot 8$ の識別」**、**「$5$ の合成（$2+3$ 等）」**、**「$10$ の補数」**、**「繰り上がり（$8+5$ 等）」**の課題ごとに、どの数字の組み合わせで時間がかかっているかを色分け表示する。
3. **プレイ履歴タイムライン＆データ管理機能**
   * 日別のプレイ履歴一覧表示。
   * **JSONエクスポート / インポートボタン：** ブラウザのキャッシュクリアに備え、記録データをファイルとしてダウンロード・復元できる機能。
   * **CSVダウンロードボタン：** Excelやスプレッドシートで詳細分析したい場合に出力できる機能。

## 6. 推奨ディレクトリ・ファイル構成案

ご主人がメンテナンスしやすく、後から新しいゲーム案（ファイル）をポンと追加できる構成案です。単一HTMLファイルでプロトタイプを作る場合も、内部のクラス構造をこの単位で分けておくと拡張が容易です。

```text
math-craft-game/
├── index.html               # エントリポイント（画面枠・モード切替UI・ダッシュボードモーダル）
├── css/
│   └── style.css            # 共通スタイル・アニメーション定義（合体・分裂エフェクト等）
└── js/
    ├── main.js              # アプリ初期化・画面遷移管理
    ├── core/
    │   ├── GameRegistry.js  # 各ゲームモード（案A〜D＋新規案）の登録・切替管理
    │   ├── ProblemEngine.js # 学習課題（2+3, 6・7・8, 繰り上がり等）の出題ロジック
    │   └── StorageManager.js# localStorageへの保存・集計・JSONエクスポート処理
    ├── dashboard/
    │   └── AnalyticsView.js # 保護者用の結果振り返り・グラフ描画コンポーネント
    └── modes/               # ★新しい案を思いついたら、ここにJSファイルを追加するだけ！
        ├── ModeANumicon.js  # 案A：偶奇・対称パズル（ヌミコン×テトリス型）
        ├── ModeBRods.js     # 案B：カラーロッド・クラフト（キュイゼネール型）
        ├── ModeCSlimeRPG.js # 案C：スライム・オーバーフロー（繰り上がりRPG型）
        └── ModeDGuildCoin.js# 案D：ギルドの高速両替商（人生ゲーム通貨型）
```

### 新しいゲーム案を追加する際の手順（3ステップ）
1. `js/modes/` フォルダ内に新しいファイル（例：`ModeEMonsterCard.js`）を作成する。
2. 共通インターフェース（`init`, `loadQuestion`, `destroy`）に沿って画面表示とクリア判定を記述し、クリア時に `context.onComplete({ isCorrect, mistakeCount, responseTimeMs })` を呼び出す。
3. `GameRegistry.register(ModeEMonsterCard)` を1行呼ぶだけで、トップ画面のモード選択ボタンと保護者用ダッシュボードの集計対象に自動的に追加される。

## 7. 学習目標・仮説・検証計画

### 7.0 到達目標の定義（v2.1 新設）
本アプリの到達目標は、**数の合成・分解・位取りを「構造から導ける状態」**にすることとする。

| 区分 | 内容 | 本版での扱い |
|---|---|---|
| 構造理解 | 8+5 を「10と3」として組み立て直せる。13−5 を「10を開いて5と5」として説明・再現できる | **目標** |
| 導出方略 | 覚えていない組み合わせを、知っている構造（10のまとまり、ペア、5のまとまり）から導ける | **目標** |
| 表現間の対応 | 同じ数量関係を、形・長さ・10フレーム・通貨で見つけられる | **目標** |
| 即答の自動化（流暢性） | 計算カードのように見た瞬間に答えが出る | **本版の目標に含めない** |

- 自動化を目標外とする理由：10-09 の検査記録の統合分析では、遅さが「自動化を要する変換」に集中し、意味・文脈・構造を使った経路で補っていることが示唆されている（解釈・推測）。反復による自動化を狙う設計は、この補償経路と逆方向になる可能性がある。
- 流暢性を将来扱う場合は、別フェーズとして本人・保護者が判断し、本書を改訂する。

### 7.1 事実・仮説・判断の区別

**(a) 保護者からの報告**（検査で確認されたものではない）
- 掛け算・割り算、人生ゲームのお札計算は得意。
- 1桁の足し算（2+3 など）、6・7・8 の識別、位取り・繰り上がり・繰り下がりでつまずく。
- 水道方式の動画（同色・縦1列のタイル）を見ているときに生あくびが続いた。

**(b) 検査記録**（出典：保護者の非公開記録。数値は本リポジトリに記載しない）
- 入力側の強さ：視知覚（特に形の恒常性）、構成・推理、言語理解が強い。
- 自動化を要する変換の遅さ：処理速度、数字の読み上げ速度、眼と手の協応、視覚運動統合が弱い。
- 単純な記憶より、組み替えて活用する課題に強み（検査者所見）。
- 単一の複雑な図形の記憶は弱く、単純な図形の連続の記憶は強い。
- 検査値は算数のつまずきの原因を直接証明しない。

**(c) 本人の語り**（出典：`記録_2026-09-03 そわそわと心の中の仕組み`）
- 周りの声を聞きにくくするために、ぼーっとしたり、**あくびをするふり**をすることがある。
- 好きなのは「物と物を組み合わせると新しいものができるゲーム」。母が「テトリスやぷよぷよのようなくっつけるパズル？」と尋ねると、本人は**それとは違う**と答え、素材を掛け合わせて別の物にするゲームだと説明した。
- 楽しすぎると、楽しさとそわそわは距離が近いので、そわそわのほうに行ってしまう。
- 無理に努力しようとすることも、そわそわにつながる。
- 母が怒ると、そわそわが注がれるのと同じ。楽しいこと・嬉しいことがあると少し減る。
- 朝はぼんやり、昼に向けて上がり、夕方に下がり、夜にまた上がる。

**(d) 検証仮説**
- **H1**：2列形状のまとまりは6/7/8の弁別を助ける。
- **H2**：空席が見える10フレームは10の補数の理解を助ける。
- **H3**：既知の交換ルールは位取りへの接続を助ける。
- **H4**：操作負荷を下げると、算数の理解を観察しやすくなる。
- **H5**：別表現への転移が起きれば、個別の操作手順だけではない理解を示唆する。
- **H6（v2.1追加）**：6/7/8 のつまずきがどこにあるかは未特定である。候補は ①量の弁別、②数字記号の読み・呼称、③量と記号の対応づけ。数字を読み上げる課題の遅さは②③の可能性を残す（推測）。
- **H7（v2.1追加）**：「組み合わせると新しいものが生まれ、図鑑に残る」というクラフトの枠組みは、本人の語った好みに合い、自発的な再挑戦を増やす。

**(e) 記録から導いた設計判断**

| 記録 | 設計判断 | 本書の該当箇所 |
|---|---|---|
| あくびのふりは本人の自発的な工夫 | あくびを疲労・失敗のサインとして記録・表示しない | §11.1、受け入れテスト10・17 |

### 7.2 課題と評価
| 課題 | 最初の観察 | 転移課題 | 遅延確認 |
|---|---|---|---|
| 6/7/8識別（量） | 同一配置で選択 | 色や向きを制御した別配置 | 別日に同じ数量を識別 |
| 数字と量の対応（v2.1追加） | 量を見て数字カードを選ぶ／数字を見て量を選ぶ | 別モードの量と数字を対応づける | 別日に再現 |
| 5までの合成 | 2+3の形の結合 | ロッド・コインで同値を再現 | 別日に再構成 |
| 10の補数 | 8の空席2を認識 | 10ロッドの不足部分を選択 | 別日に8と2を再現 |
| 繰り上がり | 8+5の10と3を観察 | 別表現で10+3を構成 | 別日に再現 |
| 繰り下がり | 13−5の交換過程を観察 | 通貨交換で同じ差を示す | 別日に再現 |

- 「数字と量の対応」は H6 の切り分けに使う。量だけの課題と数字だけの課題の結果を比べることで、つまずきの所在を推定する材料にする。口頭での読み上げは求めない。
- 成績は `assistanceLevel` で「自力・ヒント後・実演後・未完了」の4区分に分ける（§10）。
- 少数試行でモードの優劣を断定しない。提示順・既習度・操作方法・難易度・時間帯を記録する。
- 反応時間は補助指標であり、成功の主要基準ではない。
- 本人の楽しさ・自発的再挑戦・中断希望を重視する。保護者の主観的観察は明示的に別欄にする。

### 7.3 学習進行モデル
`explore（自由探索）→ observe（観察）→ predict（予測）→ construct（本課題）→ transfer（別表現）→ revisit（後日再確認）`
- `construct`（本課題）は、初回の表現で §9.0 の決定点を行う段階とする（旧§17の実装判断を v2.6 で正式に仕様化した）。`transfer`・`revisit` は同じ決定点を別表現・別日で行う。
- `observe`（観察）も決定点がないため、`explore` と同じく `outcome: "explored"` で閉じ、成績に算入しない。
- 後日再確認（`revisit`）は、前日以前に完了した問題を3回に1回程度もう一度出し、`revisit` として記録する（旧§17）。
- **おまかせ進行**（`freeChoice`、初期OFF。旧§18.2）：ホームでモードをタップするとすぐ始まり、課題・段階はモードごとの「課題の順 × 観察→予測→本課題」のステップのうち、まだ済んでいない最初のステップから出す。ステップが「済んだ」のは、同じステップをヒントなし・間違いなしで2回続けて解けたとき（間にスキップ・ヒント・間違いがあれば続けてとは数えない。途中で離れた試行は数えない）。観察は「みた！」まで進めれば済む。反応時間は判定に使わない。できなかったときに前のステップへ戻さない。全部済んだら最後の本課題をくり返す。`freeChoice` を ON にすると課題・段階の選択画面を出す。
- 進行は強制しない。自由に戻れる。
- 予測は選択式を標準とし、説明の言語化を必須にしない。
- 予測の選択は `prediction_made` イベントとして記録する（v2.1）。
- 予測の直後には正誤に関係なく仕組みを確認できる。
- 転移では数値ペアを維持し、表現だけを変更する。
- `explore` の試行は正答判定の対象外とし、成績集計に算入しない（v2.1）。

### 7.4 観察計画（単一事例での比較）（v2.1 新設）
- **本人の選択を優先する。** 本人が選んだモードで遊ぶことを妨げない。その結果、モード間比較は統制された実験ではなく「観察」として扱い、ダッシュボードでもそう表示する。
- 本人に特に希望がない日に限り、保護者がその日の最初のモードを日替わりで入れ替える（提示順の偏りを減らすため）。
- 試行ごとに時間帯（朝・昼・夕方・夜）を記録し、比較は同じ時間帯どうしで行う。
- モード間比較を表示する最低件数は「モード×課題ごとに10試行かつ3日以上」を初期値とする。これはAIが置いた暫定値であり、保護者が設定で変更できる。

### 7.5 学校の算数との接続（v2.1 新設）
- 学校では「さくらんぼ計算」の表記が使われる前提で、任意の「数で見る」表示の最終段階に、学校の表記との対応を出せるようにする。
- 本人が望まない限り表示しない。学校の表記を正解の形として扱わない。
- 学校の時間制限つきの計算練習（計算カード等）への対応は本アプリの範囲外とする。学校との調整が必要かどうかは保護者が判断する。

## 8. UI・アクセシビリティ要件

### 8.1 必須操作
- すべての課題をタップだけで完了可能にする。標準はダイレクト操作（次項）。ダイレクト操作が OFF のときは「アイテムをタップ→置き先をタップ」で完了できる。
- **ダイレクト操作**（`directManipulation`、初期ON。旧§18.1）：手札は1回タップすると置き先へ吸い込まれて置かれる（オートスナップ）。C・D の配置は「ちぎる位置」を物の上でタップして決め、判定はちぎられた個数に対して行う（決定点の値は §9.0 のまま）。吸い込みの演出はアニメーションとして扱い、操作不能時間は反応時間から除く。動きを減らす設定・速さ「すぐ」では飛ばさずにすぐ置く。
- ドラッグ、スワイプ、キーボード操作は追加可能だが必須にしない。
- タップ領域は 48×48 CSSピクセル以上、隣接する対象との間隔は 8 CSSピクセル以上を初期値とする。
- 選択中のアイテムは静的な枠線で示す。同じアイテムを再タップすると選択解除。
- ドロップ先は十分に大きくし、スナップ判定を広くする。
- 誤操作には即時減点せず、取消・やり直し（一手戻し）を用意する。
- アニメーション中の操作不能時間は学習反応時間から除く。

### 8.2 刺激調整
- `quietMode` を実装し、点滅、ファンファーレ、過度な動きを無効化する。
- 空席の標準表現は静的な輪郭・明度差。点滅は標準では使用しない。
- OSの `prefers-reduced-motion` に対応する。
- 音声は初期状態OFF。**音なしで全課題が完了できる**ことを必須にする。
- 次問の自動開始は禁止。毎問「もう一度」「次へ」「おしまい」を選べる。
- 中断、スキップ、戻るを常時利用可能にする。中断を失敗扱いしない。
- 色だけで数を識別させず、形、長さ、配置等を併用する。
- 数式は出題画面に強制表示しないが、任意の「数で見る」切替を用意する。

**v2.1 追加**
- **演出の上限**：成功演出の強さは `effectLevel: "none" | "calm" | "normal"` で指定し、初期値は `calm`。正解が続いても演出を強めない。連続正解数、コンボ、星の数を子ども向け画面に表示しない。てんすう・ランク・ランキングの扱いは直後の「てんすう・ランク・ラウンド」に従う（v2.2 の保護者判断で §8.2 の旧規定を置き換えた）。
- **誤答の表現**：赤い×、ブザー、揺れ、「ざんねん」等の表示を使わない。棒がはみ出す、プレートが枠に収まらないなど、**形が合わない様子そのもの**で示し、そのまま取り消せる状態にする。
- **声かけの文言**：「がんばれ」「あと少し」「早く」など努力や速さを促す文言を使わない。表示する文言は事実の描写（「ここがあいているよ」）にとどめる。
- **ノルマを設けない**：日ごとの目標や達成度を子ども向け画面に出さない（ラウンドの進み具合の表示は §8.2 てんすう項のとおりで、ノルマとしては扱わない）。
- **数字のふだ**（`numberLabels`、初期ON。v2.4・旧§20、本人の希望による）：むれ・へや・手札の**数**は数字で見せてよい。ただし、たし算・ひき算の**式**と**答え**は、今までどおり「かずで みる」のときと、試行が終わってからだけ出す。OFF にすると形だけの表示に戻る。判定する場面（決定点）と、違うときに形で見せることは変えない。

**てんすう・ランク・ラウンド**（`scoreEnabled`、初期ON／`roundLength`、初期10。旧§18.3・§21 を統合）
- 1問の点（v2.5）：ヒントなし・1回目でぴったり 10／ためしてから当たった 3（ヒントのあとも同じ）／ヒントのあと1回目でぴったり 6／実演のあと 4／予測が外れたが最後まで見た 2／観察を最後まで見た 2／別の世界（表現横断）でも1回目でぴったり +5／図鑑に新しい発見が増えるごとに 5。
- **点は減らない**（間違い・スキップ・中断で引かない。0より下にならない）。**速さで点を変えない**。連続正解の倍率・コンボ・時間制限は設けない。1回目でぴったりのときは、点のふだに「いっぱつ！」を添える（演出の強さは `effectLevel` のまま）。
- 点・ランクは記録（試行の結果と `roundId`）から毎回計算し、別に保存しない。ただし点の付け方を変えるときは**基準点**（`profile.scoreBaseline`）を1回だけ保存する：合計点は「基準点 ＋ それ以後（基準時刻以降）の記録を新しい付け方で数えた点」とし、点・ランクが下がらないようにする。ランキングでも基準点より前のラウンドは前の付け方の点で残す。
- ランク（合計点で決まる。植物の成長）：たね 0 → めばえ 30 → ふたば 100 → わかば 200 → つぼみ 350 → はな 550 → み 800 → き 1100 → おおきな き 1500 → もり 2000 → おおきな もり 3000 → もりの しま 4500 → みどりの ほし 6500 → ほしと つき 9000 → ぎんが 12000。
- ラウンド：既定10問。上部に葉の数で進み具合と、そのラウンドの点を出す。毎問「もういちど／つぎへ／おしまい」は今までどおり（自動で次へ進まない）。ランキングは**本人の過去のラウンドだけ**（ほかの人とは比べない）。最後までやったラウンドだけを点の高い順に並べる。保護者画面で表示を OFF にできる。

### 8.3 共通レイアウト
- 主な操作対象は中央固定フレーム内に置く。
- 不必要なオブジェクト移動を禁止する。許可する動きは、本人の操作の結果としての移動と、§9 で定義した分解・合体の演出のみ。
- モバイル画面で横スクロールなしを目標とし、拡大表示に対応する。

**v2.1 追加**
- **参照を消さない**：目標の枠、比較対象、元の数量は、操作中ずっと画面に残す。見せてから隠して覚えさせる課題を作らない。
- **手順は単純な状態の連続で見せる**：分解・合体の各段階を1つずつ表示し、直前の状態を縮小表示で残す。1枚の複雑な図にまとめて見せない。

### 8.4 保護者画面への入り口（v2.1 改訂）
- 長押しだけでは誤進入があるため、2本指で画面の2隅を同時に長押しするなど、**計算を使わない**確認方法にする。実装方式（旧§17）：画面の左上と右上の隅を同時に1.5秒長押しする。同時押しができない環境（マウスなど）向けに「左上を長押し→3秒以内に右上を長押し」も受け付ける。画面のヘッダーは左右56pxをゲート用に空ける。
- 計算問題による保護者ゲートは使わない（本人にとって算数の課題になり、かつ本人には解けてしまうため）。
- これはセキュリティ機能ではなく誤操作防止である。

### 8.5 本人向けの表示：クラフト図鑑（v2.1 新設・要承認）
- 合成・分解で作ったもの（例：「2と3で作った5」「8と2で作った10」）を、本人が見返せる図鑑として残す。
- 図鑑に表示するのは**作ったもの**だけとし、正答率・速さ・ヒント回数・ミス回数は表示しない。
- 同じ数を別の組み合わせで作ると、図鑑の同じページに組み合わせが増えていく（例：5のページに「2と3」「1と4」「4と1」）。
- 本人が望めば、セッションの終わりに「どうだった？」を3択（よかった／ふつう／たいへんだった）と「こたえない」で記録できる。初期設定はOFF。
- **実施状況（v2.6）**：図鑑は実装済みで初期ON（保護者画面でOFFにできる）。作ったものだけを表示し、まだ作っていない空きページは出さない（収集のプレッシャーを避けるため）。本人の自己報告は初期OFF。図鑑の記録には v2.3 で種類（`kind`、§9.6）を追加した。本節の当初の位置づけは「要承認の提案」であり、承認・実装の経緯は §16 に残す。

## 9. モードの改訂仕様（4モード＋じっけんラボ）

### 9.0 全モード共通（v2.1 新設）

**数の範囲**
- Phase 1〜4 の出題は 0〜20 に限る。
- v2.7：範囲は課題ごとに検証する（`valueRange`）。0〜20 は従来の課題の範囲として変えない。はんぶんチャレンジ（`halving`）だけ、出題値・答え・選択肢の元になる値を 1〜9999 とする（§9.7）。
- 繰り上がり：被加数・加数とも1〜9、和が11〜18。
- 繰り下がり：被減数11〜18、減数2〜9、被減数の一の位 ＜ 減数。
- 100（金貨）は Phase 4 の範囲外。表示はできるが出題しない。

**決定点（本人が決める点）**
自動アニメーションは観察支援であり、再生されたこと自体は正答ではない。正答判定は以下の決定点に対してのみ行う。

| モード | observe（観察） | predict（予測） | 本課題・transfer |
|---|---|---|---|
| A 偶奇パズル | 判定なし | 合体後の形を候補から選ぶ | 識別：シルエットに合うプレートを選ぶ／合成：残りの枠を埋めるプレートを選ぶ |
| B カラーロッド | 判定なし | つないだ長さがどの棒と同じかを選ぶ | 隙間を埋める棒を選ぶ |
| C 10のへや（旧スライム） | 判定なし | 空席に入る数／あふれて残る数を選ぶ | 10のまとまりと残りを構成する |
| D 両替商 | 判定なし | お釣りの組み合わせを選ぶ | お釣りのコインを選んで渡す |

- `explore` 段階には決定点を置かない。
- ラボモード（§9.6）のうち決定点があるのは F シーソーの「つりあわせる」だけであり、決定点は §9.6 に定義する。E・G・H は決定点を置かず、発見を図鑑に残す。

**選択肢（ダミー）の設計**
- 6/7/8 の識別では、**同じ偶奇の選択肢を必ず含める**（6に対して8、7に対して9または5）。偶奇の違いだけで解ける問題にしない。
- 選択肢は2〜4個。初期値は3個。

**ヒントの段階**
| 段階 | 内容 |
|---|---|
| L1 | 静的な合図（目標の枠や空席の輪郭を濃くする）。文章による説明はしない |
| L2 | 候補を2つに絞る |
| L3 | 実演（一連の操作をスロー再生で見せ、もう一度本人が行えるようにする） |

- L1・L2 を使った正答は `after_hint`、L3 の後の正答は `after_demo` として記録する。

**色の扱い**
- 色の割り当ては全モード共通の `colorScheme` で管理する：`"cuisenaire"`（B の標準配色を全モードに適用）／`"unified"`（独自の共通配色）／`"mono"`（単色＋形・長さのみ）。
- モードごとに別々の配色を使わない（別表現への転移で、色が手がかりを混乱させないため）。
- 赤・黄緑・濃緑（2・3・6）は色覚の違いで見分けにくいことがある。長さ・形だけで解けることを受け入れテストで確認する。

**クラフトとしての枠組み**
- 合成の結果は「消える」のではなく「新しいものになって図鑑に残る」演出にする（§8.5、H7）。
- テトリス型の「そろえると消える」報酬は使わない。

### 9.1 A：偶奇・対称パズル（v2.1 改訂）
- **向き**：プレートは **2行×n列（横向き）** で描く。各列が2個のペア。奇数の余り1個は**最終列の上段**に置く。
  - 6 = 2行×3列、8 = 2行×4列、7 = 2行×3列＋最終列の上段に1個。
  - 理由：C の10フレーム（2行×5列）とマスが一致し、A で作った形をそのまま C のフレームに重ねられるため。v2.0 の「3行×2列（縦向き）」から変更した（§16 の要確認事項）。
- **識別課題では回転しない**。プレートは常に上記の基準の向きで出す。
- **奇数＋奇数（例：3＋3）の合体**：
  - 2枚目を180°回転させ、1列分左へずらすと、互いの1個がかみ合って長方形（6）になる。
  - この回転は**システムのアニメーションが行い、回転の過程を見える形で再生する**（スロー可）。本人に回転操作を求めない。
  - 回転の前後を並べて表示し、向きが変わっても同じ数であることを示す。
- **偶数＋任意**：回転なしで横につなぐ。偶数のプレートを左に置く（奇数の余り1個が常に最終列に来るようにするため）。本人が奇数を左に置いた場合も、アニメーションで並べ替えて同じ基準の形にする。
- 数値ごとの色固定は `colorScheme` に従う。色だけで正解できない比較課題を含める。

### 9.2 B：カラーロッド
- ロッドの長さの単位倍率は全問で一定にする。目盛りの扱いは `rodGrid`（初期ON。v2.2・旧§18.6 が v2.1 の「目盛りなし」を保護者の判断で置き換えた）：背景に1ずつの目盛り線（点線。5と10は太い実線）と、はじめの5のまとまりに薄い色の帯、下にものさしの目盛りを描く。棒の中にも1ずつの区切りを描き、5のところは太くする（手札の棒も同じ）。**数字は書かない。** OFF にすると目盛りなしの棒に戻る。長さをくらべる手札は縦に並べて左端をそろえる。
- 単位長は「10本分が中央フレームの幅に収まる最大値」とし、最小の画面でも1と2の長さの違いが目で分かることを受け入れテストで確認する。
- 比較する棒は左端を揃え、長さの終点を静的な枠で示す。
- ヒントは §9.0 の段階式とし、色名の暗記を前提としない。
- 2+3=5 のヒントに 2+2+1 を使う場合は「別の組み方」として表示し、唯一の正解経路としない。
- 誤答（長すぎる・短すぎる）は、棒が枠からはみ出す／足りない様子で示す。

### 9.3 C：10のへや（旧スライム・オーバーフロー。v2.4 でタイル化し改名）
- 個々の対象は四角いタイルで描き、10のまとまりは「10」のカードとして扱う（v2.4・旧§20。本人の感想による）。
- 10フレームは2行×5列。空席は静的に強調する。
- **埋め方** `tenFrameFill`：
  - `"pairs"`：左の列から上下1組ずつ埋める（A のプレートと一致）。**初期値。**
  - `"fives"`：上段5個を埋めてから下段（5のまとまりを強調）。
  - どちらが合うかは未確定（§13）。設定と試行ごとの値を記録する。
- **繰り上がり a + b の一般規則**：
  - フレームに先に入れるのは大きい方の数（初期値）。設定で「先に出た数」に変更できる。
  - フレームに a があるとき、b を「10−a」と「a+b−10」に分ける。「10−a」が空席に入り10のまとまりになり、「a+b−10」が一の位に残る。
  - 例：8+5 → 5 を 2 と 3 に分ける → 8+2 で10 → 10と3で13。
- **繰り下がり（10の位 t、一の位 u、減数 b、u ＜ b）の一般規則**：
  - 初期値は**減加法**：10 を「b」と「10−b」に分ける → b を取り除く → 「10−b」と u を合わせる。
    - 例：13−5 → 10 を 5 と 5 に分ける → 5 を取り除く → 5 と 3 で 8。
  - 設定で**減減法**に切り替えられる：b を「u」と「b−u」に分ける → u を取り除く → 10 から「b−u」を取り除く。
    - 例：13−5 → 5 を 3 と 2 に分ける → 3 を取り除く → 10 から 2 を取り除いて 8。

- **E タイル・リアクター**（`arrays`、自由探索のみ）：タイルを +1・+5・−1 で入れ（1〜36個）、「ならべる」（1〜6行）で並び直す。割り切れると欠けのない長方形になり図鑑へ。2〜6行を全部ためして長方形にならなければ「1列にしか並ばない特別な石」（素数）として図鑑へ。ためした並べ方は縮小表示で残す。「スープ」の画面は材料×トッピングの組み合わせを格子に並べ、2×2以上で長方形と同じ記録にする。
- **F シーソー**（`balance`、本課題＋自由探索）：重りは いろぼう と同じ長さ・色・区切り。左右の合計が同じなら水平、違えば重い方へ傾く（傾きは1回だけゆっくり変わり、揺れつづけない）。本課題「つりあわせる」は、左の重さ t（6〜18）、右に c（1〜9）があり、右に足す重り（t−c、1〜9）を選ぶ。ヒントは §9.0 の段階どおり。自由探索では釣り合い（両側に重りがあり、左右が同じ組み合わせではないもの）を図鑑に残す（左右を入れかえても同じ記録）。
- **G ばいばいラボ**（`doubling`、自由探索のみ）：ふえる（×2・×3・×10 を選んで「1にち すすむ」。64までは1つずつ、それより多いと 1・10・100・1000・10000 のまとまりで見せる。「1にち もどる」で戻れる。1から同じ倍率で2日以上すすむと図鑑へ）と、わける（タップで半分に分ける。1/16まで。「がったい」で同じ大きさどうしが合わさる。元の大きさの輪郭はいつも見えている。全部が同じ大きさになると図鑑へ）。

- 見送った案と理由は旧§19.5（履歴）に残す。

### 9.8 J ジオボード（v2.8・図形の基本・第1段）

釣り合い・長方形・倍と半分・周期（§9.6）の次の段階として、図形の基本（直角・三角形・四角形・長方形・正方形）を、数字を介さずに触れる自由探索として加える。§0〜§9.5 の規則（時間制限なし、誤りを示す印を出さない、参照を消さない、音は初期OFF、演出は `effectLevel` まで、タップで完結）はすべて守る。

- **モード**：`mode_j_geoboard`（課題 `shapes`、演算 `draw`）。`group: 'lab'`。自由探索のみで、決定点・ラウンド・点数はない（図鑑の新しい発見に §8.2 の点が入る）。
- **ジオボード**：5×5 の点。点を順にタップするとゴムがかかる。**3つ以上つないだあとにさいしょの点をタップする（または「とじる」）と、輪がとじて**形のなまえが出る。
- **線の規則**：はじめは たて・よこの線だけ。「ななめも つかう」は本人が選ぶ（線を引いている途中では切りかえられない）。同じ点・来た道をもどる線・ほかの線と交わる／ふれる線は引けない。引けないときは、「ほかの てんを えらんで みよう」「たてか よこに すすめるよ」と中立に知らせるだけで、本人の失敗としては扱わない。引ける点にはうすい輪が出る。
- **直角の印**：つないだ線のかどが直角（頂点の2辺の内積が 0）なら、小さな四角の印をつける。直角でないかどには何も出さない。試行中は途中のかどに、とじたあとはすべてのかどにつく。声かけは「まっすぐな かどが ふたつ」（ひらがなの数）。数字は出さない。
- **形のなまえ**：一直線上に並んだ途中の点は、かどに数えない。かどが3つ → さんかく（直角が1つ以上なら ちょっかく さんかく）／4つ → しかく（4つとも直角なら ちょうほうけい、さらに隣りあう辺の長さが等しければ せいほうけい）／5つ以上 → たかくけい。ななめに置いた長方形・正方形も同じ規則で判定する。
- **図鑑**：`CraftKind` に `shape` を加える。`value` はかどの数、`parts = [形の記号]`（1 さんかく・2 ちょっかく さんかく・3 しかく・4 ちょうほうけい・5 せいほうけい）。たかくけいは残さない。同じ形は重複して記録しない。
- **ヒント・もどす**：決定点がないのでヒントはない。もどす（1手ずつ）と「さいしょから」は使える。
- **実装**：純粋関数は `src/core/math/shapes.ts`（React に依存しない）、画面は `GeoboardMode.tsx`、図鑑・ふだの絵は `ShapeGlyph.tsx`。

### 9.10 L タイルの かけわり（v2.10・掛け算・割り算）

本人の得意（掛け算・割り算）を足場に、範囲を広げ、2けた×1けたを「10と のこり」に分ける考え方へつなぐ。E タイル・リアクター（§9.6）の自由探索は変えない。

- **モード**：`mode_l_arrays`（`group: 'core'`）。課題は `array_multiply`・`array_divide`・`array_split`（演算 `multiply`／`divide`、段階は `construct` のみ）。盤は E と同じ `TileField`（`src/modes/shared/`）、並びの純粋関数は `src/core/math/tiles.ts`、この課題の純粋関数は `src/core/math/arrays.ts`。ホームで「じゆうに あそぶ」を選ぶと、L でも E と同じタイルの自由探索になる。
- **「れつ」**：E と同じく、よこの ならび（行）のこと。式は「1れつの数 × れつの数」（1つ分 × いくつ分）で書く。
- **課題（おまかせ進行の順）**：
  1. **いくつ ある**（`array_multiply`）：r れつ × c（各 2〜9、64通り。3×4 と 4×3 は別の問題）のタイルが、ぜんぶで いくつかを選ぶ。
  2. **わけて ならべる**（`array_divide`）：左に 10こずつ ならんだ n こ（= r × c）を、右の r れつに おなじだけ ならべると 1れつ なんこ かを選ぶ（割り切れる64通り）。選ぶと、タイルが列ごとに席へ動く。
  3. **10と のこり**（`array_split`）：r れつ × c（r 2〜9、c 11〜19、72通り）。10の列（位の色の「十」）と のこりの列（「一」）に分けて見せ、ぜんぶで いくつかを選ぶ。のこりが 0 になる c = 10 は出さない。
- **選択肢**：`choiceCount` に従う（初期3）。数字のふだ ON では数字＋位のまとまりの小さな絵、OFF では絵だけ。
- **誤答候補（理由のある間違い）**：いくつ ある → たした（r＋c）を必ず、ほかは 1れつ／1列 ずれた数。わけて ならべる → れつの数と取りちがえた（r）を必ず、ほかは 1列ずれた数。10と のこり → のこりを かけわすれた（10×r＋のこりの列）を必ず、ほかは 1列ずれた数・のこりを わすれた数（10×r）・10を かけわすれた数。正答・重複・0以下は入れない。理由が足りない小さな組（2×2 など）だけ、答えのまわりで補う。
- **違う数を選んだとき**：いくつ ある・10と のこり では、選んだ数を おなじ れつ で ならべた形を下に出す（列の数がちがう・欠けた席は点線）。わけて ならべる では、選んだ数の席にタイルが動き、のこった タイルは左に のこり、あいた 席は点線になる。赤・×・音・ゆれは使わない。もどす・ほかのを選ぶで続けられる。
- **ヒント**：L1 1列ぶんを点線で囲む（わけて ならべる では r 本の れつ を濃くする）。L2 候補を2つ（正答と、いちばん起こりやすい間違い）に絞る。L3 実演：1列ずつ囲みを広げる（10と のこり では 10の列 → ぜんぶ）。わけて ならべる では正しい数で席に ならべて見せてから戻す。
- **かずで みる**：出題中は「6 × 3 = ？」「72 ÷ 8 = ？」、試行の終了後は答え。10と のこり は「10 × 6 = 60」「3 × 6 = 18」「60 + 18 = 78」「13 × 6 = 78」。
- **図鑑**：解けた配列を `product`（[れつ, 列]、値はぜんぶの数）として残す。E の長方形と同じページに並ぶ。
- **点数・ラウンド**：従来の付け方のまま（§8.2）。

本人の希望：「もっと難しい問題がやりたい」「半分にするゲームは、大きい数から半分にするほうがよい。最初は4けたのランダムな数を出し、自分で半分の数を選ぶ。その数をまた半分にすることを繰り返す」。

- **モード**：独立したモード `mode_i_halving`（課題 `halving`、演算 `halve`、段階は本課題 `construct` のみ）。決定点があるので、ホームの上段（`group: 'core'`）に置き、おまかせ進行・ラウンド・点数の対象にする。G ばいばいラボに課題を足すと、G をタップしたときにおまかせ進行が始まり、G の自由探索の入口が変わってしまうため、G には混ぜない。
- **出発値（A方式・条件付きランダム）**：1000〜9999 のうち 32 の倍数（281通り）から、ほぼ均等に選ぶ。32 の倍数なら、少なくとも 5 回は整数の半分が続く。乱数は差しかえられる純粋関数で選ぶ（テストで再現できる）。直近の出発値は避ける。前日以前に始めた出発値をときどき出す（後日再確認 `revisit`）。全4けたから一様に選ぶ方式（B方式）は、最初から奇数になりうるため、まだ作らない（§13）。
- **1試行＝1回「半分を選ぶ」**。決定点は「今の数の半分を、選択肢から選ぶ」。選択肢の数は `choiceCount` に従う（初期3）。
- **見せ方**：今の数を 1000・100・10・1 のまとまり（千のかたまり・百の板・十の棒・一の四角）で見せる。数字のふだ ON のときは今の数と選択肢を数字でも見せる（式は出さない）。手札には数字と、位のまとまりの小さな絵を出す（数字のふだ OFF では絵だけ）。一度に描くのは各位 19 こまでで、数千このタイルは描かない。
- **正しく選んだとき**：上の位から順に、ふたつの おさら へ同じ数ずつ分ける様子を1つずつ見せる。ある位のまとまりが奇数なら、1つを「ひらいて」下の位の 10 こにする（C・D の「10を ひらく」と同じ考え方）。前の状態は縮小表示で残す。もとの数はいつも見えている。
- **違う数を選んだとき**：選んだ数を ふたつの おさら に置き、「ふたつ あわせると」の量がもとの数と合わない位を点線のわくで示す。赤・×・音・揺れは使わない。もどして選びなおせる。
- **誤答候補**：(1) 奇数の位をひらかずに各位を半分にした数（例 7424 → 3212。奇数の位がなければ正答と同じなので出さない）を必ず入れ、(2) 半分を2回した数、(3) 2倍にした数からランダムに補う。足りないときだけ、位の1つ分（1000・100・10・1）違う数で補う。正答・重複・0以下は入れない。
- **ヒント**：L1 位の名前（せん・ひゃく・じゅう・いち）と区切り線、（数字のふだ ON なら）位ごとの数を静的に出す。L2 いちばん上の位だけ分けたところを薄く見せ、候補を2つ（正答と「ひらかずに分けた」数）に絞る。L3 全部の位を順に分けて見せてから元に戻し、本人が選びなおす（実演後の正答は `after_demo`）。
- **つぎの問題（自動では進めない）**：試行が終わったら、本人が「この かずで もういちど」「もう はんぶん」（選んだ半分がつぎの問題の数になる）「あたらしい 4けた」「おしまい」から選ぶ。半分を選べなかった（スキップ）ときは「もう はんぶん」を出さない。半分が奇数になったら、その列はそこまで（失敗ではない。小数・分数へは進まず、勝手に丸めない）。
- **連続の記録**：1つの出発値から始まる列を `Question.chain`（`id`・出発値 `initial`・何回目の半分か `step`）で関連づける。問題IDは `halving:<今の数>`。`Session ＞ Trial` の2階層は変えない。決定のたびに `decision_made` の `payload` に `chainId`・`step` を残す。
- **点数**：従来の付け方のまま（§8.2）。何段目でも同じ点で、続けるほど増える倍率はない。速さでは変えない。
- **かずで みる**：出題中は「7424 の はんぶん は ？」、試行の終了後は「3712 と 3712 で 7424」「7424 の はんぶん は 3712」。
- 図鑑には記録しない（v2.7 時点）。

## 11. ログ・分析・永続化（v2.6 で保存方式と型を本文化）

### 11.1 スキーマ
保存は IndexedDB を標準とする（DB 名 `math_craft_app_data_v2`。旧§17の実装判断を正式化）。データ形式の版はスキーマ内の `schemaVersion: "2.1"` で区別し、互換性のため仕様書の版（v2.6）とは切り離して据え置く。

記録は **セッション（1回の着席）＞ 試行（1問）** の2階層とする。v2.0 の `PlaySession` は1問単位だったため `Trial` に名称を変更した。

- **時間帯の境界**（端末のローカル時刻。旧§17）：朝 5:00–10:59、昼 11:00–15:59、夕方 16:00–18:59、夜 19:00–4:59。
- **保護者観察欄に行動の解釈を選択肢として用意しない。** v2.0 の `yawningObserved`、`fatigueReportedByChild` は削除した。あくびは本人が自分の工夫として語っているため、「あくびあり＝負荷が高い」という読み方を記録の形で固定しないためである。気づいたことは `note` に自由記述する。

### 11.2 指標の定義
- `firstActionLatencyMs`：最初の `input_enabled` から最初の入力まで。未入力ならnull。
- `activeInteractionMs`：`input_enabled` 中、かつポーズ・非表示でない時間の合計。アニメーションの操作不能時間は除く。
- `animationDurationMs`：演出開始〜終了の合計。
- `idleDurationMs`：入力可能中、定義済み閾値を超えた無操作時間の合計（閾値は `LearningSettings.idleThresholdMs`、初期値10秒）。
- `hintCount`、`maxHintLevel`、`mistakeCount`、`outcome`、`assistanceLevel` を別々に集計。
- `longLatencyFlag` は相対的な長考の記述的フラグであり、疲労や逐次数えの推定には使用しない。
- `visibility_hidden` から `visibility_visible` までの時間は全指標から除く。

### 11.3 ダッシュボード
- モード別に課題カテゴリ、難易度、学習段階、**時間帯**を揃えて比較する。
- 「速さの順位」より、独力達成率・ヒント依存・転移・後日再現・本人の選好を中心に表示。
- 件数と日数を必ず併記し、§7.4 の最低件数に満たない場合は比較を表示しない。
- 本人の選択による観察であり、統制された比較ではないことを比較画面に明記する（§7.4）。
- 「正答率が高い＝このモードが合っている／負担が小さい」と自動で判定・表示しない。
- 保護者観察・本人の自己報告・機械ログを明確に区分する。
- JSONインポートは形式・バージョン検証、重複ID検出、プレビュー、復元前バックアップを行う。
- CSVはセッション単位・試行単位・イベント単位を別出力にする。
- **匿名化エクスポート**：`playerLabel` と自由記述欄を除いた出力を選べる。学校・医療機関・他のAIに渡す場合はこちらを使う運用とする。
- 表示時刻は端末のタイムゾーン（日本標準時）。保存はオフセット付きISO8601。
- データは原則端末内保存。外部送信・第三者解析を行わない。
- 保存領域の容量逼迫時は古いログを勝手に削除せず、エクスポートを案内する。保存は IndexedDB を標準とする（実装済み）。`localStorage` は v1 からの移行元としてのみ参照する。

### 11.4 v1 からの移行（v2.1 新設）
| v1 の項目 | v2.1 での扱い |
|---|---|
| `logs[]` | 1件ごとに `Trial` を作る。日付（日本時間）ごとに1つの `Session` にまとめ、`endReason: "unknown"` とする |
| `timestamp`（UTC） | オフセット付きISO8601に変換して `Session.startedAt` に入れる |
| `modeId`、`taskCategory`、`numbers`、`targetAnswer` | `Question` の `representation`、`taskType`、`operands`、`expectedValue` |
| `problemKey` | `Question.id` の生成に使う |
| `isCorrect` かつ `usedHint === false` | `assistanceLevel: "independent"` |
| `isCorrect` かつ `usedHint === true` | `assistanceLevel: "after_hint"`（v1 ではヒントと実演を区別できないため） |

## 12. 実装フェーズ・受け入れ基準

### Phase 1：共通基盤＋A
- タップのみで全課題が完了できる。
- 6/7/8の配置に一貫性がある（2行×n列、奇数の余りは最終列の上段）。
- 識別課題に同偶奇のダミーが必ず含まれる。
- 自由探索・観察・予測が切替可能。

### Phase 2：B＋表現横断
- 同一問題ID・数値関係を維持してA/Bを切り替えられる。
- 長さが表示倍率によって数学的に破綻しない。
- 色だけを手がかりにせず解ける。
- `colorScheme` を切り替えても A と B の配色が一致する。

### Phase 3：C
- §9.3 の一般規則に従い、対象範囲のすべての組み合わせで分解・合体を正しく表示する。
- 減加法・減減法の切替、`tenFrameFill` の切替が機能する。
- スロー再生・途中停止・一手戻しが機能する。

### Phase 4：D
- 5トークンON/OFFで交換規則が矛盾しない。
- 同じ数量関係を通貨と他モードで比較できる。

### 18.1 ダイレクト操作（`directManipulation`、初期 ON）
- 手札（`ChoiceTray`）は、1回タップすると置き先へ吸い込まれて置かれる（オートスナップ）。OFF なら v2.1 の「選ぶ→置き先をタップ」。ドラッグは今までどおり任意。

- **決定点を「ちぎる位置」にする**（C の フレーム・バス、D の 1のへや・ねだんカード）：むれを 2行の並びで大きく出し（各 48px 以上）、j 番目をタップすると、はじめから j 番目までの k 個がちぎれて置き先へ入る。判定は k に対して行う（§9.0 の決定点の値は変わらない）。違う k のときは、すきまが残る／はみ出す様子のまま止まり、もどす か 別の位置を選び直せる。
- ダイレクト操作では、置き終わったあとの「？の箱」を選ぶ手順（C の繰り下がり D2、D のおつり D2）を省き、仕組みを最後まで見せて終わる。予測（predict）は今までどおり形を選ぶ（1タップで置ける）。

### 18.2 おまかせ進行と適応型スキップ（`freeChoice`、初期 OFF）

### 18.3 てんすう・ランク・ラウンド・植物（`scoreEnabled`、初期 ON／`roundLength`、初期 10）
- 1問の点：ヒントなし 10、ヒント後 6、実演後 4、予測が外れても最後まで見たら 2、観察を最後まで見たら 2、別の世界（表現横断）でもできたら +5。図鑑に新しい組み合わせが増えるごとに 5。
- **点は減らない**（間違い・スキップ・中断で引かない）。**速さで点を変えない**。連続正解の倍率・コンボ・時間制限は設けない。
- ランク（合計点で決まる）：たね → めばえ → ふたば → わかば → つぼみ → はな → み → き → おおきな き → もり。ホームと結果画面に、ランクに合わせて育つ植物を出す。
- ラウンド：既定 10 問。上部に葉の数で進み具合と、そのラウンドの点を出す。毎問「もういちど／つぎへ／おしまい」は今までどおり（自動で次へ進まない）。最後の問題のあと「けっかを みる」で、点・植物（ランクが上がったら並べて見せる）・自分の記録のランキングを出す。
- ランキングは**本人の過去のラウンドだけ**（ほかの人とは比べない）。最後までやったラウンドだけを、点の高い順に並べる。

### 18.4 両替（D）の見せ方
- 位ごとに色を分けた「へや」：10のへや（青）、1のへや（黄）、りょうがえマシン（緑）。見出しにコインの絵を添え、色だけに頼らない。
- 1のへやに 10 の席を描き（5トークン OFF のとき）、マシンの中に「1 が 10 まい → 10 が 1 まい」の絵を描く。1のへや → マシン → 10のへや の流れを矢印で示す。
- 繰り上がりの本課題（ダイレクト操作・5トークン OFF）：もらうコインの「ちぎる位置」をタップして 1のへやの空席へ入れる。ぴったり 10 枚になると両替が起きる。
- 引き算（加数法）：**もっている お金のうち 10 だけで はらい、1 は持ったまま**にする。ねだんのカードが 10 になるまでの おつりと、持ったままの 1 を合わせたものを「のこる お金」として見せる（v2.1 の「はらった お金」表示では、4えんの ものに 12えん はらうように見えたため）。

- 手札（コインの組み合わせ）は、**金種ごとの列**に分けて並べる（大きい金種が左、各列は2行）。列の幅は選択肢の中の最大枚数でそろえ、金種のあいだに すきま と うすい仕切り線 をおく。どの選択肢でも 10 の列と 1 の列が同じ位置に来るので、10 と 1 が混ざって見えない。答えの箱の中も同じ並べ方にする。

- ホームに「じっけん ラボ」の段を設け、4つのモードを並べる（`GameModePlugin.group = 'lab'`）。
- 決定点のないモード（E・G・H）は、タップするとすぐ自由探索として始まる（ラウンド・点数はない）。発見は図鑑に残り、図鑑の1件ごとに 5 点（§18.3）が入る。
- 決定点のあるモード（F の「つりあわせる」）は、おまかせ進行・ラウンド・点数の対象になる。
- 図鑑の記録に種類（`CraftEntry.kind`）を加えた：`product`（長方形 [行, 列]）、`prime`（素数の石 [n]）、`balance`（釣り合い。左の重り…, 0, 右の重り…）、`power`（倍々 [倍率, 日数]）、`fraction`（1 を [d] こに わけた）、`period`（れっしゃ [a, b]、値は最小公倍数）。v2.1 の合成（`sum`）は種類なしのまま同じキーで扱う。
- 出題（決定点）の範囲は 0〜20 のまま。自由探索では 20 をこえる数（タイル 36 まで、ばいばい 99999 まで、線路 60 まで）を形で見せる。数字は数字のふだ（`numberLabels`）に従う（v2.7 後に「数字は出さない」規定を撤回。§9.6）。

### 19.1 E タイル・リアクター（`arrays`、自由探索のみ）
- タイルを +1・+5・−1 のボタンで入れる（1〜36 個）。「ならべる」ボタン（1〜6 行の絵）で、列ごとに上から並び直す（2 行は A の偶奇プレートと同じ並び）。
- 割り切れると欠けのない長方形になって縁が光る（2 行以上・2 列以上のとき図鑑へ）。割り切れないと最後の列が欠け、欠けた席は点線で残る。
- 2〜6 行（n−1 まで）を全部ためして、どれも長方形にならなければ「1列にしか並ばない特別な石」（素数）として図鑑に残る。36 以下では 6 行まで試せば必ず判定できる。
- ためした並べ方は縮小表示で残す。ボタンには、ためした印（点）がつく。
- 「スープ」の画面：材料（色と模様で区別する4種）× トッピング（形の4種）を選ぶと、組み合わせが格子に並ぶ。2×2 以上で長方形と同じ記録として図鑑へ。

### 19.2 F シーソー（`balance`、本課題＋自由探索）
- 重りは いろぼう と同じ長さ・色（1 目盛りずつの区切り、5 で太線）。左右の合計が同じなら水平（いつも見えている水平線が光る）。違えば重い方へ傾く。傾きは1回だけゆっくり変わり、揺れつづけない。
- 本課題「つりあわせる」：左の重さ t（6〜18。10 をこえたら 10 と のこり の2つ）、右に c（1〜9）。右に足す重り（t−c、1〜9）を選ぶ。違う重りでは傾いたまま。もどす か ほかの重りで置きかえられる。ヒントは §9.0 の段階（L1 右の皿を強調、L2 2つにしぼる、L3 正しい重りを半透明で見せる）。
- 自由探索：左右に重りを置く（皿の重りはタップで下ろせる。1皿 8 個まで）。両側に重りがあり、左右が同じ組み合わせではない釣り合いを図鑑に残す（左右を入れかえても同じ記録）。
- 負の数（浮く風船）は今回は入れていない。

### 19.3 G ばいばいラボ（`doubling`、自由探索のみ）
- ふえる：×2・×3・×10 を選び「1にち すすむ」。64 匹までは1匹ずつ（親から分かれて出てくる）、それより多いと 1・10・100・1000・10000 のまとまりで見せる（ゼロの位は空の列として見える）。「1にち もどる」で戻れる。すすんだ日は太陽の印で並ぶ。1 から同じ倍率で2日以上すすむと図鑑へ。
- わける：スライムをタップすると半分に分かれる（1/16 まで）。「がったい」で同じ大きさどうしが合わさり、最後は元の大きさにもどる。元の大きさの輪郭はいつも見えている。全部が同じ大きさになると図鑑へ。

### 19.4 H ぼうの れっしゃ（`period`、自由探索のみ）
- うえ・した の列車の棒（1〜10）を選び、「のばす」で短い方の列車に1両足す（同じなら両方）。端がそろった位置には線と星の印が残る。最初にそろう位置が最小公倍数。
- 線路は 60 目盛り（1・5・10 の目盛り線、端にかべ）。かべまでにそろわない組み合わせもある。
- 「どんどん のばす」は1両ずつ見せて進み、とめる・もどす が使える。時間で勝手に進むことはない（§19 の評価で、時間で回る歯車・公転の案を、この形に置き換えた）。
- ちがう長さ（どちらも 2 以上）が初めてそろうと図鑑へ。

### 19.5 見送った案（理由）

- 落ちる玉の分かれ道（ガルトンボード）：本人が決める場面がなく、本書の到達目標（構造から導ける）から遠い。後日、おまけの実験として検討する。

## 20. v2.4 数字タイル（2026-10-19・本人の感想と保護者の判断）

> **v2.6 での位置づけ：本節は履歴である。** 規範的な内容は本文（§0・§7〜§14）へ統合済みであり、本節と本文が矛盾する場合は本文が優先する。

本人の感想「スライムの形が嫌い。数字のほうがいい」を受けて、保護者が「数字タイル」を選んだ。§0・§8.2 の「数式は出題画面に強制表示しない」のうち、**むれ・へやの数を数字で見せること**を、本人の希望で置き換える。たし算・ひき算の**式**と**答え**は、今までどおり「かずで みる」のときと、試行が終わってからだけ出す。

- スライムの形をやめた（C 10の へや、G ばいばいラボ、ちぎる手札、ホームのアイコン）。1つ1つは四角いタイル、10 のまとまりは「10」のカード（中に 2行×5列 の目）。モード C の名前は「10の へや」にした。
- `numberLabels`（初期 ON。保護者画面「数字のふだ」で OFF にできる）：
  - C：10のへや・1のへや・待っているむれ・バス・あふれた分に、今の数のふだを出す。手札のむれは大きな数字＋小さなタイルの並び。ちぎる手札のタイルには、はじめから何枚目かの数字を書く（「ここまで k こ」）。

  - OFF では v2.3 までと同じく形だけ（スライムではなくタイル）。
- 数字が見えても、判定する場面（決定点）と、違うときに形で見せること（はみ出す・すきまが残る）は変わらない。

### 20.1 手札の棒・重りを場と同じ大きさに（2026-10-19・本人の様子から）
- 棒を選ぶとき、手札の棒が小さく、2 なのか 3 なのか分かりづらかった。
- B（いろぼう）の識別・合成・予測と、F（シーソー）の「つりあわせる」では、手札の棒・重りを、場にある棒・重りと**同じ長さ・太さ・区切り**で描く（場の SVG の表示倍率を測って合わせる）。手札は縦にならべて左端をそろえる。
- 自由探索の手札（1〜10 が全部並ぶ）は、場所をとるので今までどおり小さめ。
- ただし F の自由探索は、手札を左右で1組にまとめ、場と同じ大きさで 1〜5 と 6〜10 の2列に並べた。乗せる皿は「ひだりへ／みぎへ」か、皿をタップして選ぶ（選んでいる皿は輪郭が濃くなる）。

## 21. v2.5 てんすうの見直し（2026-10-20・本人の様子と保護者の判断）

> **v2.6 での位置づけ：本節は履歴である。** 規範的な内容は本文（§0・§7〜§14）へ統合済みであり、本節と本文が矛盾する場合は本文が優先する。

本人はすぐに一番上のランク「もり」まで進んだ。楽しくて一気に進んだもので、進みの速さは問題にしない（図鑑の発見の点も、上限をつけずにそのまま）。一方で、あてずっぽうで押している様子があった。v2.4 までは、ヒントなしなら何回まちがえても 10 点だったため、考えずに押しても点が同じだった。

- **1問の点**：ヒントなし・1回目でぴったり 10、ためしてから当たった 3（ヒントのあとも同じ）、ヒントのあと1回目でぴったり 6、実演のあと 4、予測が外れた 2、観察を見おわった 2、別の世界でも1回目でぴったり +5、図鑑の新しい発見 5。
- 間違いで点を引くことはしない（0 より下にならない）。速さでは変えない。連続正解の倍率はつけない。
- 1回目でぴったりのときは、点のふだに「いっぱつ！」を添える（演出の強さは effectLevel のまま）。
- **基準点**（`profile.scoreBaseline`）：新しい付け方にした最初の起動のとき、それまでの記録を前の付け方で数えた点を1回だけ保存する。合計点は「基準点 ＋ それ以後の記録を新しい付け方で数えた点」。点・ランクが下がらない。ランキングでも、基準点より前のラウンドは前の付け方の点で残す。
- **もりの先のランク**（宇宙が好きなので、森 → 島 → 星 → 銀河）：おおきな もり 3000、もりの しま 4500、みどりの ほし 6500、ほしと つき 9000、ぎんが 12000。
